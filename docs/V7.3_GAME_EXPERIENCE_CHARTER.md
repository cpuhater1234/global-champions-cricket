# GCC v7.3 Game Experience Charter

## Status

v7.2.16 Launcher Fast Path is frozen as the last accepted v7.2 baseline.

v7.3 changes the development mode from incremental screen polish to coherent game-experience building. The simulation, player database, ratings, season engine and dynasty persistence remain protected unless a reproducible defect is found.

## Product objective

Global Champions Cricket should be immediately understandable, difficult to master and difficult to put down for one more season.

The player should understand the interface quickly. The difficulty should come from cricket judgement, uncertainty, trade-offs and consequences.

## Canonical dynasty loop

Start career
-> choose club
-> Signing Week
-> Draft Order
-> Draft
-> choose XI
-> play season
-> react only when a meaningful decision is required
-> Finals
-> Season Review
-> offseason changes
-> market / trades where relevant
-> annual Draft
-> Final 15
-> choose XI
-> next season

The loop is judged as one product rather than as a collection of individually successful screens.

## Product laws

1. The human player owns the important cricket decisions.
2. The game may recommend, explain, order and warn; it must not silently solve a meaningful human decision.
3. Simulation should move quickly until the player genuinely needs to act.
4. A new season is a new cricket state, not a cheaper version of the interface.
5. One interaction pattern should own one job across the game.
6. Routine administration should be quiet. Ceremonial cricket moments should have weight.
7. Comprehension comes from hierarchy and cricket language, not more boxes, badges or tutorial chrome.
8. If a screen already achieves its job, leave it alone.

## Canonical interaction families

### XI selection

One squad-selection language for foundation year and later seasons.

Required states:
- 0/11
- partial XI
- 11/11
- direct bench swap
- batting-order editing
- injury-required change

All 15 squad players remain visible while selecting. Selected and unselected state must be obvious. The user chooses the eleven.

The game may:
- offer short squad-balance guidance
- warn about no recognised keeper
- warn about insufficient bowling cover
- naturally order the selected eleven
- expose conditions and opponent context

The game must not:
- offer a one-click complete recommended XI
- silently repair the human XI after an injury

### Player pool / recruitment

The foundation Draft establishes the canonical player-pool experience:
- focused pool
- search
- BAT / WK-BAT / AR / BOWL filters
- progressive deeper access
- squad-needs context
- deliberate secondary full-board view

Annual Draft should use the same interaction family, adapted to its smaller pool and shorter draft.

Replacement-player markets and future trade/free-agent work should reuse the same player evaluation language where appropriate rather than inventing separate admin interfaces.

### Season decision hierarchy

Every season state should answer:
1. What just happened?
2. What is next?
3. Do I need to decide anything?

If no meaningful human decision exists, the game should keep moving.

## Protected strong areas

Do not broadly redesign without new evidence:
- Signing Week structure
- Draft Order reveal
- core 2008 Draft architecture
- Season Hub
- Finals
- Season Review
- offseason stage rhythm
- simulation/database/dynasty persistence systems

## v7.3 build sequence

### v7.3.0 Core Game Experience

Own the XI decision:
- remove the complete-XI recommendation gateway
- show the full squad throughout selection
- clean PICK / selected / swap interaction
- preserve natural batting-order assistance
- preserve cricket-balance warnings
- interrupt human auto-simulation when XI action is genuinely required
- never silently auto-repair the human XI

### v7.3.1 Dynasty Continuity

Bring the annual Draft onto the canonical Draft interaction architecture while preserving the annual two-round rules and existing CPU/dynasty logic.

### v7.3.2 Cricket Language & Comprehension

Audit major screens in journey order. Add or rewrite only the minimum cricket-specific direction needed to answer what the player must decide and why it matters.

### v7.3.3 Visual Identity

Refine the GCC mark and launcher masthead as one coherent premium cricket identity. Retain cream/muted green. Remove nested visual furniture rather than adding ornament.

### v7.3.4 Golden Dynasty

Run a controlled 2008-2010 dynasty repeatedly. Classify every issue as:
- KEEP
- REBUILD
- CONSOLIDATE
- CUT

No generic "polish a bit" bucket.

## Acceptance gates

Every coherent build must pass two independent gates.

### Engineering gate

- deterministic rebuild from exact accepted parent
- protected systems unchanged outside explicit allowlist
- JavaScript syntax clean
- save/resume integrity
- no duplicated players or invalid XI state
- desktop and mobile browser coverage
- no page-level overflow
- no runtime/page/console errors

### Game gate

- the player immediately understands the current decision
- the player, not the computer, owns the important cricket choice
- the interaction matches the same job elsewhere in the game
- the screen does not add needless administrative friction
- the build does not make the cricket easier merely by automating it
- the result creates consequence, uncertainty or attachment
- repeated-season use is considered, not only first-use appearance

A build that passes engineering but fails the game gate is rejected.

## Golden dynasty test

The minimum full-product QA journey is:

### 2008
Fresh career -> club -> Signing Week -> Draft Order -> full Draft -> manual XI -> full season -> Finals where applicable -> Season Review.

### 2009
Full offseason -> annual Draft -> Final 15 -> manual XI -> season -> forced injury decision -> replacement market where legitimately required -> mid-season trade window -> Finals/Review.

### 2010
Advance far enough to verify the repeated loop remains coherent, fast and recognisably the same product.

The purpose is not merely bug detection. It is to judge whether another season remains compelling.
